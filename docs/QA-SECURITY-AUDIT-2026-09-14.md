# Waw Marketplace — Full-Site QA & Security Audit (Launch-Readiness Report)

**Date:** 2026-09-14 · **Scope:** All three roles (Customer, Seller, Admin) + cross-cutting security
**Method:** Code-level end-to-end journey audit (static analysis of `apps/web`, `apps/seller`, `apps/admin`, `apps/api`, `supabase/migrations`, env/deploy configs), cross-checked against the prior audit (`QA-SECURITY-AUDIT-2026-09-13.md`), plus live verification via the API unit-test suite (**120/120 passing**: RBAC, inventory locking, refunds, guest tokens, reservation expiry, cookie serialization, upload sniffing).
**Live browser testing caveat:** The stack was not running locally (Docker/DB/Redis required), so UI findings are derived from tracing real code paths (form → API client → route → service → SQL/RPC) rather than screenshots. Every finding cites file:line for reproduction.

---

## Executive Summary — Verdict: **NO-GO for launch**

The server-side authorization architecture is genuinely strong (Redis-backed opaque sessions, DB-authoritative roles, `requireRole` middleware, migration 049 RLS hardening, CSRF double-submit with timing-safe compare, 13 purpose-built rate limiters, atomic settlement RPCs, refund idempotency-by-construction, 120 passing unit tests). The launch blockers are all at the **seams between apps** — response-shape contracts, enum mismatches, and validation mismatches that silently break the exact flows a real user needs on day one.

### Top 5 Launch Blockers

1. **Every variant product on the storefront shows "Out of Stock" and cannot be purchased.** The products API doesn't select `offer_variants.stock_quantity`, so the web mapper computes stock = 0 for all variant products (`product.service.ts:189`, `web api.ts:33-71`, `ProductDetailClient.tsx:543`). The majority of a multi-vendor catalog is unpurchasable.

2. **The seller journey cannot operate end-to-end.** (a) The storefront `/sell` application **always fails**: the form requires dashed CNIC (`XXXXX-XXXXXXX-X`, 15 chars) but `SellerApplySchema` requires exactly 13 digits (`sell/page.tsx:81` vs `schemas.ts:164`) → every submission 400s. (b) The seller portal's **Edit Product silently drops price, stock, category, image, and weight changes**: it sends snake_case keys (`base_price_pkr`, `stock_quantity`, `image_url`…) that Zod's camelCase `UpdateProductSchema` strips as unknown → the modal says "Product updated" but only title/description persist (`seller lib/api.ts:477-486` vs `schemas.ts:53-67`). (c) Coupon min-spend/cap are silently zeroed by the same class of bug (`minSpendPkr` vs `minOrderPkr`).

3. **Money-path integrity failures in Admin.** (a) Dispute resolution's "Refund Buyer" is a financial **no-op** — the panel sends `REFUND_ISSUED`/`CLAIM_REJECTED`/`REPLACEMENT_SENT`, the service matches `REFUND_BUYER`/`RELEASE_SELLER_PAYOUT`/`REPLACEMENT_ISSUED`, so disputes close as "resolved" with **no refund and no payout hold** (`admin lib/api.ts:330-334` vs `support.service.ts:14-18,349,389`). (b) Admin panel order cancellation bypasses the atomic `cancel_order` RPC — no inventory release, no payout cancellation, no payment reversal (`admin orders/page.tsx:156-173` vs `order.controller.ts:275-294`). (c) Marketplace pricing settings (commission, GST, fees) have zero server-side validation — a single bad PATCH corrupts every future order's math (`schemas.ts:156-159`).

4. **The buyer session/checkout chain de-links orders and strands guests.** (a) The web app never calls `/api/auth/session/refresh`; after 15 minutes every authenticated call 401s, order history silently shows "No orders," and checkout falls back to **guest mode so signed-in buyers' orders aren't linked to their accounts** (`session.controller.ts:21-29` vs no refresh call anywhere in `apps/web/src`). (b) The merged user cart is never fetched after login+refresh — the cart appears to vanish. (c) Guest + Raast: the order is created, then payment initiation 401s (endpoint requires auth) with the cart uncleared and a fresh idempotency key per click → **duplicate orders on retry**. (d) The 7-day return flow **always fails** — the web never sends `items`, which the service requires.

5. **Moderation & secrets gaps.** (a) Banned users can un-ban themselves: the 049 trigger only guards `role`, but the `profiles` UPDATE policy still lets row owners set `is_banned = false` (`001:777` + `049:28-46`). (b) The current `.env` carries `RAAST_WEBHOOK_SECRET=REPLACE_WITH_GENERATED_48_CHAR_SECRET` — a placeholder that **passes** the production blocklist; anyone holding it can forge "payment received" webhooks (`env.ts:179-200`). (c) The Typesense server key and `NEXT_PUBLIC_TYPESENSE_API_KEY` are the same value — the browser-exposed key had verified admin privileges in the prior audit; rotation/purge status is still unresolved.
